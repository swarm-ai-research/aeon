## Findings

### Confirmed dependency CVEs

**1. `esbuild@0.27.7` — GHSA-g7r4-m6w7-qqqr — LOW (dev, Windows-only)**

- **Ecosystem:** npm, **Group:** `dev` (transitive via `tsup@^0.27.0`).
- **Range:** `>=0.27.3 <0.28.1`. **Fixed in:** `0.28.1`.
- **Impact:** Path traversal in the `esbuild --servedir` HTTP dev server on Windows. `path.Clean()` normalizes `/` only, so backslash traversal escapes the served root and reads arbitrary files.
- **Reachability for torlink:** none in production. torlink is a terminal client; it does not run `esbuild --servedir`. The bump is hygiene — it clears the advisory from `npm audit`, `osv-scanner`, and Dependabot for anyone consuming the lockfile in CI.
- **Route:** public PR drafted at `.pending-disclosure/baairon-torlink-2026-07-04T160000Z.md`. Adds an `overrides` block in `package.json` pinning `esbuild` to `^0.28.1`, forcing the fix into the whole tree without waiting for `tsup` to publish a compatible release. **Not submitted from Aeon** because the GitHub Actions token cannot fork upstream repos (403 "Resource not accessible by integration") — operator must fork with a PAT and open the PR.

**2. `ip@2.0.1` — GHSA-2p57-rm9w-gvfp — HIGH (transitive, unpatchable)**

- **Ecosystem:** npm. Transitive via `webtorrent` → `bittorrent-tracker` → `ip@^2.0.1`.
- **Range:** `>=0 <=2.0.1`. **Fixed in:** *none — `last_affected: 2.0.1`, no `fixed` event*. The `ip` package is unmaintained.
- **Impact:** `isPublic()` misclassifies addresses like `127.1`, `01200034567`, `::fFFf:127.0.0.1`, `012.1.2.3` — SSRF-classification bypass. Incomplete fix for CVE-2023-42282.
- **Reachability for torlink:** low. `bittorrent-tracker` uses `ip` for peer-address classification (filtering out private ranges from the peer list), not for outbound URL validation. torlink is a local CLI, not a server, so an attacker cannot feed IP strings across an authenticated request boundary; the worst case is a malicious tracker response causing the client to attempt a peer connection to an internal address — no data exposure, no cross-tenant impact.
- **Route:** **cannot bump — no fixed version exists.** A torlink-scoped PR cannot resolve this; upstream fix would need to land in `bittorrent-tracker` (migrate off `ip`). Logged here for the local report only; not disclosed.

### Code findings (candidates)

- **Semgrep confirmed vulnerabilities:** 0 across 96 scanned paths (0 ERROR, 0 WARNING). One partial-parse warning on a `.test.ts` file (already excluded by the runtime `--exclude=test`).
- **TruffleHog verified secrets:** 0 in working tree, 0 in git history.
- **Manual review candidate (not disclosed):** `saveTorrentMeta(id, data)` at `src/download/persist.ts:76-83` builds `path.join(torrentsDir, ${id}.torrent)` without validating `id`. `id` traces back to `TorrentResult.infoHash`, which for the `piratebay`, `nyaa`, `rss`, `x1337`, `eztv`, and `yts` sources is the raw `info_hash` / `hash` field from the search API with only `.toLowerCase()` applied (see `src/sources/piratebay.ts:28`, `src/sources/nyaa.ts:24`, `src/sources/rss.ts:21`). A malicious or MITM'd search endpoint could return `info_hash: "../../evil"` and, *if* `WebTorrent.add()` accepted the resulting magnet and its `onMetadata` callback fired, torlink would `writeFile` to a path outside `torrentsDir`. Real-world exploitability is low: `WebTorrent` almost certainly rejects non-hex40 / non-base32-32 infohashes at magnet parse time, and the attacker also needs the user to select the malicious result and start the download. **Filed as a hardening note only** — the repo has no PVR / no `SECURITY.md`, so per the skill's "do no harm" rule this stays in the local report and is not published as an issue or PR. Suggested fix if the maintainer stumbles on this report: reuse `normalizeInfoHash` from `src/sources/magnet.ts` and drop results whose `info_hash` doesn't match `/^[a-f0-9]{40}$|^[a-z2-7]{32}$/i` before they reach the queue.
