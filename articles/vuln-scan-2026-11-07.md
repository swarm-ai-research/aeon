**`cryptography 48.0.1` CVEs (macOS Intel wheel only):**

1. `GHSA-g6cj-pr64-35w5` / `PYSEC-2026-3552` — **PKCS#7 EnvelopedData** Bleichenbacher oracle via distinguishable errors/timing. Code path: `cryptography.hazmat.primitives.serialization.pkcs7` decryption APIs.
2. `GHSA-jwv3-5hgf-82ww` / `PYSEC-2026-3553` — **X.509 path-building** exponential-time on duplicate self-signed intermediates. Code path: `cryptography.x509.verification`.
3. `GHSA-m2h6-j472-rp4c` / `PYSEC-2026-3554` — **X.509 verifier** accepts wildcard DNS names escaping `permittedSubtrees`. Code path: `cryptography.x509.verification`.

**Why none are reachable from this codebase:** `grep -rn "from cryptography" scan/zbtriage/` shows the production code imports **exactly** `cryptography.hazmat.primitives.ciphers.{Cipher,algorithms,modes}` and `cryptography.hazmat.primitives.keywrap.aes_key_unwrap` — AES-CBC and RFC-3394 AES Key Wrap. The three advisories concern PKCS#7 and X.509 modules that this codebase never imports or invokes. The maintainer documents this directly in `requirements-backups.txt` ("Its open advisories concern X.509 verification and PKCS#7, which this tool does not use (only backup decryption).") and implicitly acknowledges in-scope boundaries in `SECURITY.md`.

**Why no bump PR is possible:** PyPI's `cryptography` dropped Intel-macOS wheels after 48.0.1. There is no newer wheel to pin to for that platform; a bump would force Intel-Mac users to a source build (a toolchain cliff that defeats the `--require-hashes --only-binary=:all:` posture). This is a documented, scoped risk-accept — the same pattern as `guillaumemeyer/watermarks-remover` on 2026-08-22, where no public dep-bump PR was filed because the upstream offered no fixed version on the pinned platform.

**No PR action.** Not a zero-day to disclose; already-public CVEs with no reachable gadget, filtered by the maintainer's own documented scope.
