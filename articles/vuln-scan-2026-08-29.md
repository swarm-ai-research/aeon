## Candidate → confirmed

- **4 semgrep candidates → 0 confirmed.** All four are `dockerfile.security.missing-user` on the top-level `Dockerfile:217`, `agent-computer/Dockerfile:31`, `agent-langgraph/Dockerfile:20`, `supervisor/Dockerfile:24`. **Discarded — deliberate pattern, exhaustively documented in-repo:**
  - Top-level `Dockerfile:186-201` carries a 15-line comment `"NOTHING THAT MATTERS RUNS AS ROOT"` explaining that s6-overlay init stays root *precisely so it can drop each supervised service to a distinct UID* (`pwuser` for browser + API, `postgres` for the DB) — a shared account would put the process rendering the open internet in the same skin as the one holding the audit trail.
  - `agent-computer/Dockerfile` is the Bot's *own computer*: an isolation container run one-per-Bot per the deployment guide, protected by gVisor at the platform layer + `--security-opt no-new-privileges` at the runtime layer. Running Chromium `--no-sandbox` as pwuser vs. root here is not the real boundary; the container is.
  - `agent-langgraph/Dockerfile` + `supervisor/Dockerfile` follow the same s6-drop pattern.
  - Rewriting these to `USER pwuser` would break s6's ability to fork services under different UIDs. Reporting them as findings would be reporting on a design choice the maintainer has documented in-line and reasoned about explicitly.
- **0 verified secrets** — TruffleHog fs and git-history walks both returned empty. The 19KB `.env.example` is placeholders; no `.env` in tree; no `id_rsa` / `.pem` / KEK material.
- **16 vulnerable dep packages** — see next section; **0** routed to a public PR.

## Manual code review (targeted, on the high-value surfaces the scanners under-cover for agent-runtime code)

- **`agent-computer/src/workspace.ts`** — three-layer path confinement (absolute-path refusal → lexical containment → post-symlink `realpath` check), plus explicit `writeDestination` walk with `MAX_LINK_HOPS = 32` to catch symlinks planted through a prior write. Author has clearly anticipated and countered every canonical traversal pattern including the "link at the last component" variant that most refuse-list guards miss. Nothing to flag.
- **`agent-computer/src/shell.ts`** — env allowlist (PATH + LOCALE + TERMINAL + PROXY only; proxy userinfo stripped before propagation), `BASH_ENV` / `LD_PRELOAD` / `IFS` / `CDPATH` on an explicit `NEVER_PASSED` deny-list, `bash -c` (not `-lc`) to skip `.bash_profile` sourcing on a workspace HOME, min/max timeout bounds, process-group SIGKILL on abort or timeout, 64KB output cap trimmed *while it arrives* not at end, with the truncation flag preserved through the trim. Author documented all of it. Nothing to flag.
- **`server/src/computer/target.ts`** — SSRF guard for Bot navigation and separate one for supervisor callback URLs. `NEVER_ALLOWED_HOSTNAMES` covers AWS/GCP/Azure metadata IPs, IPv6 `fd00:ec2::254`, ECS/Fargate `169.254.170.2`, Alibaba `100.100.100.200` (CGNAT, not RFC1918). `canonicalHostname` unwraps `::ffff:0.0.0.0`, `64:ff9b::/96` NAT64 embedded IPv4, and trailing-dot spellings before matching. `isPrivateIpv6` covers `fe80::/10` link-local, `fc00::/7` unique-local, `::`, `::1`. Every escape hatch (`allowPrivateHosts`) is checked *after* `isNeverAllowedHostname`, so no configuration reopens cloud metadata.
- **`server/src/agents/endpoint.ts`** — `createAgentFetch` re-runs `checkAgentEndpoint` on every redirect hop, not just the first, and carries `allowPrivateHosts` + `allowedHosts` to each hop. Redirect-chain SSRF via 302 to a private host is refused.
- **`agent-computer/src/authorisation.ts`** — constant-time `matchesToken` (length-check then XOR-fold), single centralised `ACTING_PATHS` set used by the dispatcher rather than per-handler guards (comment cites a prior incident where `/exec` was added and missed a per-handler check — hence the centralised list).
- **`server/src/plugins/oauth.ts`** — token-exchange and DCR registration `fetch`es use `redirect: "manual"` and `AbortSignal.timeout(15_000)`; `tokenUrl` / `registrationUrl` sourced from a pinned catalogue, not user input. JSON parse is `.catch(() => null)` so a captive-portal HTML body cannot throw out of a refusal path.
- **`.github/workflows/{ci,release,publish-release}.yml`** — every `${{ github.* }}` / `${{ needs.*.outputs.* }}` / `${{ steps.*.outputs.* }}` interpolation into a `run: |` block goes through an `env:` mapping (no direct injection into bash string context). All external actions SHA-pinned. All `actions/checkout` steps use `persist-credentials: false`. `pull_request`-triggered image build is gated behind a `full-ci` label an unprivileged forker can't add. The `verify` job aggregates `needs.*.result` (fail-fast pattern that treats a *skipped* required job as pass but a *cancelled* one as fail). The kind of CWE-78 shell-injection I flagged last week on `guillaumemeyer/watermarks-remover` (`${{ github.ref_name }}` in a `packages:write + id-token:write` job) does not exist here — checked release-images / publish-release specifically, both clean.

Net: this is one of the most defensively-written agent runtimes I've audited. Every check has a comment explaining *why* it exists and *what earlier bug it caught*, which is unusually strong signal that the maintainer thinks about the boundary rather than the ideal path.

The maintainer explicitly *chose* to keep npm dep-management manual — a `.github/workflows/security_zizmor.yml` is present, so security is not off the radar, but npm bumps are their reviewed gate rather than a Renovate firehose. Filing an issue would fit here better than a PR, but the skill's rule is *don't publish anything a maintainer didn't ask for* when the fix isn't clean and net-positive; this qualifies.
