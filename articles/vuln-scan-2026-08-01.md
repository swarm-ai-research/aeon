## Confirmed findings

### 1. Weak GCM authentication tag validation in shared `decrypt()` helper

- **Severity:** Low (defense-in-depth; no end-to-end exploit chain in
  current callers)
- **Class:** CWE-354 (Improper Validation of Integrity Check Value) +
  CWE-310
- **Location:** redacted (see PVR draft) — one file, three lines away from
  the fix.
- **Channel:** **Private Vulnerability Report** →
  `.pending-disclosure/talivia-group-talivia-2026-08-01T160000Z-pvr.md`
- **Rationale for PVR (not public PR):** the code is unpatched; publishing
  file/line in a public issue or PR would hand attackers the exact reach
  vector before the maintainer has a patch. Suggested `authTagLength`
  addition is a one-line fix, so the disclosure window should be short.
- **Reachability:** the helper is called (a) with attacker-controlled input
  from `Authorization: Bearer <token>` via `parseAuthToken →
  parseSecureToken → decrypt`, and (b) with server-controlled input from
  `decryptProviderSecret` and cron jobs on stored data. Path (a) is
  currently gated by an outer `jwt.verify`, which prevents end-to-end
  forgery today. The finding is filed anyway because `decrypt()` is a
  shared primitive — any future caller that trusts the plaintext without a
  strong outer verifier immediately opens a directly-exploitable path.

Full technical detail (attack primitive, PoC, suggested patch, submission
commands) is in the PVR draft. This article deliberately redacts file/line
per the skill's guidance for PVR-routed findings.
