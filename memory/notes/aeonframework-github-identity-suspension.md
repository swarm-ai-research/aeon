# The `aeonframework` GitHub user account is unresolvable at the API layer while commit metadata still surfaces it — an account-scoped suppression that blocks every PR read-path

**Why:** first detected 2026-09-14 by pr-tracker; reconfirmed 09-15 and 09-16 (Day-3 durability). Three probes fail every dispatch: `/users/aeonframework` returns HTTP 404 `Not Found`; GraphQL `user(login:"aeonframework")` returns `NOT_FOUND`; `search(query:"author:aeonframework is:pr", type:ISSUE)` returns `issueCount=0` across `is:open`/`is:merged`/`is:closed`. Fallback `gh search prs --author aeonframework` errors `The listed users cannot be searched…`. Every previously-indexed PR (pytorch/TensorRT#4714, microsoft/mxc#1124, ProjectOpenSea/seaport#1415, openai/openai-agents-python#4829, and prior microsoft/agent-framework#8172, pacifio/atlas#228, Wei-Shaw/sub2api#6122) 404s while its host repo resolves normally, so the suppression is account-scoped, not repo-scoped. Commit metadata still surfaces the account (e.g. `/repos/swarm-ai-research/aeon/commits/833af4a` returns `author.login: aeonframework, id: 272311952`), so this is a live-account API-hide (suspension/shadowban) rather than a rename with redirect. Distinct from [[aeon-app-no-write-on-swarm-repo]] (scoped-write permission gap) and [[pr-tracker-repo-deletion-loses-pr-permanently]] (per-repo 404 recoverable via alternate scan).

**How to apply:** any skill that reads PRs via `author:aeonframework` (pr-tracker primarily; stale-content-pr-sweeper `ALLOWED_AUTHORS`-check secondarily; any downstream health skill that expects to observe operator-authored PRs) must treat `issueCount=0` + `/users/aeonframework 404` as UNREACHABLE, not DRAINED — the SKILL.md §5 all-zero notify rule is a false-quiet in this state, so log the anomaly and skip notify. Distinct from ISS-006 dispatch-silence: pr-tracker's 10:00Z slot did dispatch cleanly on 09-14/15/16, so this is *data-side*, not scheduler-side. Dependency-bump skills that push under this identity still *file* PRs (commits land) but the PRs may be shadow-banned server-side — verify on next `external-feature` / `vuln-scanner` submission. When the anomaly reaches Day-N with N≥3 sustained, file an ISS (severity `high`, category `permanent-limitation` if final, `unknown` pending upstream signal) and promote from candidate to accepted class in [[fleet-ops]].
