# heartbeat's own >36h-staleness P0 check is gated on heartbeat dispatching — during an ISS-006 08Z dead-pocket stretch the self-check is invisible until the recovery run, and the freshness gap it reports is bounded by the outage length rather than the true drift

**Why:** heartbeat SKILL.md line 41 fires a P0 DEGRADED when its own `last_success` is >36h stale, but the check itself runs only when heartbeat's 08:00Z cron dispatches; on 2026-09-23 heartbeat surfaced `last_success = 2026-09-19T09:14:50Z` (~96h stale, 4 missed 08Z windows) for the first time only *because* today's manual-late 08:35Z invocation broke the streak. During the 09-19 → 09-22 dead-pocket window the operator-facing status page showed no DEGRADED signal (docs/status.md prev-stamp 09-19 09:10Z, 4 days stale) because the writer was silent, and batch-health could not file an ISS-006 tributary in the same window because batch-health lives in the same 08Z pocket and was silent for the same reason — the dead-pocket produces zero telemetry about its own duration. This is a sharpening of [[monitor-monitored-coupling]] — the coupling is not just "monitor shares a dependency with monitored fleet" but specifically "the self-freshness threshold is expressed in wall-clock hours but *measured* only on dispatch instants, so the threshold silently degenerates into `>36h ∧ dispatched-today`."

**How to apply:** treat heartbeat's >36h self-check as necessary-not-sufficient for freshness alarms; add an out-of-band ping (see [[probes-for-messages-yml-must-dispatch-outside-messages-yml]]) or a snapshot-rebase auto-commit to `docs/status.md` that fires from a workflow *outside* `messages.yml` so that the freshness dashboard degrades correctly during the very outages it's supposed to observe. When post-morteming an ISS-006 pocket-outage, do not read heartbeat's freshness gap as the true outage duration — it lower-bounds the gap (the recovery run's reported staleness) but under-counts every additional day where heartbeat *also* missed its slot. Same shape as [[iss-006-day-n-needs-witness-independent-of-outage]] and the batch-health filing gap in [[batch-health-severity-is-dom-parity-artifact-under-iss-006]]; combine all three when arguing severity for the ISS-006 per-slot cron rewrite.
