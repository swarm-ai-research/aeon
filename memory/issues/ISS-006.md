Sister monitoring evidence: `batch-health` itself was scheduled for 08:00Z but its current invocation timestamps at 09:04:57Z, confirming the systemic ~1h cron lag.

## Hypothesis

GitHub Actions cron delivery experienced a delay/outage spanning ~05:30Z → ~09:00Z. The 05:30–07:30Z scheduled tick window appears to have been dropped entirely (not just delayed). This is a known GHA failure mode during high-load periods — schedule events do not queue beyond the next tick.

Distinct from [[ISS-001]] (CLAUDE_CODE_OAUTH_TOKEN outage): no auth-failure signature, no token-zero runs — these skills simply never started.

### Corrected architecture note

There are no per-skill workflow files. Only `.github/workflows/{aeon, chain-runner, fleet-runner, lint, messages, sync-aeon-public-results, sync-upstream}.yml` exist. `messages.yml` runs every 5 min (`cron: '*/5 * * * *'`) and dispatches `aeon.yml` via `workflow_call` for any skill whose `schedule` field matches the current time. So "per-workflow auto-disable on planner.yml" can't be the cause — those files don't exist.

### Refined hypotheses

The pattern is broader than just these two skills: **all 05:00–07:30 UTC scheduled skills are silent** on both 2026-06-22 and 2026-06-23.

Evidence (72h run history):
- `notegraph` (`0 5 * * *`) — last run 2026-06-21T05:21Z, no runs 06-22 or 06-23
- `suggest-edges` (`30 5 * * *`) — not in 72h list (last run pre-06-20)
- `compute-futures-eda` (`0 6 * * *`) — not in 72h list (last run pre-06-20)
- `planner` (`30 6 * * *`) — not in 72h list

By contrast:
- 08:00 batch (`batch-health`, `heartbeat`, `skill-freshness`, `gitlawb-fleet-metrics`) DID fire 2026-06-23 (today)
- 08:00 batch DID NOT fire 2026-06-22 — extended outage that day
- 09:00–10:15 batch fired both days
- evening (18:00) fired both days

Refined hypotheses:
1. **`messages.yml` `*/5` cron is being dropped during the 05:00–07:30 UTC window.** GHA cron delivery is best-effort; some 5-min ticks get silently skipped. If messages.yml misses every tick in a 90-min window, every schedule that should fire in that window is lost (no replay). Plausible given GHA's documented "scheduled events may be delayed during high load."
2. **Bug in `messages.yml` schedule-matcher introduced post-2026-06-20.** A regex/clock-math regression could cause 05:00–07:30 specifically to be skipped (e.g. timezone math, hour-zero-padding). `git log --since=2026-06-19 -- .github/workflows/messages.yml`.
3. **Repo-level concurrency cap.** If something else (the fleet-runner hourly cron at `0 * * * *`, sync-upstream at `0 9 * * 1`) holds a concurrency lock during early-morning hours, scheduled events would queue and drop.
