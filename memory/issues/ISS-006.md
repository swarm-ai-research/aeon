## Context

Detected by `batch-health` at 08:00 UTC (actually fired ~09:05 UTC — see below). The GHA scheduler appears to have been silent across the entire 05:30–08:00 UTC window today:

- `notegraph` (05:00 daily) DID run at 05:21Z — last clean cron tick.

- The 08:00 batch (`heartbeat`, `batch-health`, `skill-freshness`, `gitlawb-fleet-metrics`) and the 09:00 batch (`issue-triage`, `github-monitor`, `fleet-control`, `pr-review`, `skill-evals`) all fired together at ~09:05Z — i.e. cron came back ~1h late and bundled both slots.

Sister monitoring evidence: `batch-health` itself was scheduled for 08:00Z but its current invocation timestamps at 09:04:57Z, confirming the systemic ~1h cron lag.

## Hypothesis

GitHub Actions cron delivery experienced a delay/outage spanning ~05:30Z → ~09:00Z. The 05:30–07:30Z scheduled tick window appears to have been dropped entirely (not just delayed). This is a known GHA failure mode during high-load periods — schedule events do not queue beyond the next tick.

Distinct from [[ISS-001]] (CLAUDE_CODE_OAUTH_TOKEN outage): no auth-failure signature, no token-zero runs — these skills simply never started.

The pattern is broader than just these two skills: **all 05:00–07:30 UTC scheduled skills are silent** on both 2026-06-22 and 2026-06-23.

1. **`messages.yml` `*/5` cron is being dropped during the 05:00–07:30 UTC window.** GHA cron delivery is best-effort; some 5-min ticks get silently skipped. 3. **Repo-level concurrency cap.** If something else (the fleet-runner hourly cron at `0 * * * *`, sync-upstream at `0 9 * * 1`) holds a concurrency lock during early-morning hours, scheduled events would queue and drop.

Every single day has a 3–6h gap that brackets the 06:00–06:30 schedule slot. messages.yml never ticks within that slot, so the schedule-matcher never gets a chance to dispatch `planner` / `compute-futures-eda`. The 05:30 daily skills survive because the 05:47-ish tick catches them; the 08:00 daily skills survive because the 08:40-ish tick catches them. 06:00 and 06:30 fall in the dead zone.

### Refined hypothesis (supersedes Day 4 matcher-bug hypothesis)

Matcher bug is **ruled out**. The matcher never gets called for 06:00/06:30 because messages.yml itself isn't running.

The active hypothesis is GHA-side: GitHub Actions is silently dropping the vast majority of `*/5 * * * *` cron ticks for this repo. Per the [GHA docs](https://docs.github.com/en/actions/using-workflows/events-that-trigger-workflows#schedule), schedule events "may be delayed during periods of high loads of GitHub Actions workflow runs" and the platform makes no guarantees of `*/5` density. We are seeing a ~97% drop rate, concentrated in a daily ~06:00–08:30Z dead zone, which suggests either:

1. GHA cron queue across the platform is most loaded in that window (Europe morning / US night handoff). Plausible: it consistently affects this slot.
2. Repo concurrency cap silently suppresses `messages.yml` runs (would require another long-running job to hold the lock — unlikely given evening ticks land fine).
3. Recent repo-level GHA quota or billing throttle (cost-report should surface this — last ran 2026-06-22, may itself be a victim).

### Updated action items (priority order)

1. **Switch off `*/5 * * * *`-driven dispatch.** Replace messages.yml's `*/5` schedule with explicit per-hour crons (`0,15,30,45 * * * *`) that exercise *only* the timeslots aeon.yml actually uses. Fewer ticks but each one is a "real" workflow, less likely to get dropped silently by GHA.
2. **Add a 06:00–06:30 belt-and-braces tick.** A 2nd workflow (`messages-morning.yml`) cron-only for that dead zone (`*/5 6 * * *`) gives redundant coverage.
3. **Compare with a fork.** If gitlawb forks running an identical `*/5` cron deliver more ticks, our quota is throttled; if they show the same pattern, it's GHA platform behavior. Cheap to check via fork-cohort.
4. Resolve only after 3 consecutive clean morning batches (raised from 2 — the pattern is sticky enough to warrant extra confirmation).

### Severity unchanged at `high`

Recurring 5-day pattern + concrete root-cause hypothesis = high. Bumping further to `critical` would require a verified loss-of-data scenario (memory-flush hasn't run for 5+ days, so MEMORY.md promotion is degraded — partial degradation but not zero).
