## Summary

Between 2026-06-19T20:25Z and 2026-06-20T01:53Z, every scheduled skill exited with `claude` CLI returning code 1 in ≈0.7 seconds. The 06:06Z recovery batch is succeeding, but the historical cumulative counts in `memory/cron-state.json` show ≥100 consecutive failures per skill — meaning this pattern is recurring, not a one-off.

The actual error text is unrecoverable from `cron-state.json` because the workflow truncates only the final 200 bytes of the JSON envelope, which is always the same `"...session_id_tail","total_cost_usd":0,"usage":{"input_tokens":0,...}` shape. Every skill's `last_error` field is therefore identical and useless for triage.

## Symptoms

- `success_rate` for ≥30 skills is 0.0 or 0.01, with `total_runs` 50–202 and matching `total_failures`.
- All entries share an identical 200-byte `last_error` tail (only the leading 7 hex chars — the end of `session_id` — differ).
- Logs show `Using direct Anthropic API` followed 0.7s later by `Claude CLI failed (truncated): <tail>` and `Process completed with exit code 1`.
- `total_cost_usd: 0` and `input_tokens: 0` in every captured envelope → no actual model call took place.
- Recovery batch at 2026-06-20T06:05–06:07Z is producing successes for every skill that has finished (heartbeat, suggest-edges, compute-pulse, github-monitor, code-health, etc.) — confirms skills themselves are correct.

## Diagnosis Notes

**Source status:** `cron_state=ok` · `issues_index=bootstrapped` · `gh_runs=ok` · `gh_logs=ok` · `git_log=skipped (no last_success window)` · `check_runs=not consulted (annotations empty for this failure mode)`

**Window:** 162 failures across the 200 most-recent runs span 2026-06-19T20:25Z → 2026-06-20T01:53Z (~5.5h). The 4 in-progress and 34 success runs sit entirely in the 2026-06-20T06:05Z+ window. No failures since the recovery.

**Why `category=unknown`:** the 0.7s fail-fast plus zero-cost JSON envelope is consistent with an Anthropic API authentication or model-availability error returning before any token is consumed, but the workflow's `tail -c 500 | cut -c1-200` strips the `result` field (which holds the actual error message). Without the real error, every category in the playbook is a guess. Per skill-repair playbook for `unknown`: document, don't edit.

**Why this is a single shared issue, not 30:** all affected skills hit the same error mode at the same wall-clock window with the identical truncated signature. Per-skill repair PRs would do nothing useful.

**Why no fix PR opened by skill-repair:** the only actionable code change is in `.github/workflows/aeon.yml` (replace `tail -c 500 | cut -c1-200` of combined stdout+stderr with `jq -r '.result // .error // .'` of the JSON envelope, so the real error text reaches `cron-state.json.last_error`). That file is on skill-repair's deny-list (constraint in `skills/skill-repair/SKILL.md` line 253). Operator must apply.

## Operator action

1. **Patch `aeon.yml` lines 511–521** to extract the JSON envelope's `result` / error field BEFORE truncating, so future failures land in `cron-state.last_error` as a human-readable string instead of an envelope tail. Suggested change:

   ```bash
   if ! CLAUDE_OUTPUT=$(echo "$PROMPT" | claude -p - \
       --model "$MODEL" --allowedTools "$ALLOWED" \
       --output-format json 2>&1); then
     # Prefer the JSON envelope's error/result field over a blind tail.
     # Fall back to the tail only if the output isn't parseable JSON.
     if SIG=$(echo "$CLAUDE_OUTPUT" | jq -r '
         if (.is_error // false) and (.result // .error // "") != ""
         then "is_error=" + ((.subtype // "true")|tostring) + ": " + ((.result // .error)|tostring)
         else empty end' 2>/dev/null) && [ -n "$SIG" ]; then
       SNIPPET=$(printf '%s' "$SIG" | tr '\n' ' ' | cut -c1-400)
     else
       SNIPPET=$(echo "$CLAUDE_OUTPUT" | tail -c 500 | tr '\n' ' ' | cut -c1-200)
     fi
     echo "::error::Claude CLI failed (truncated): $SNIPPET"
     printf '%s' "$SNIPPET" > /tmp/skill-error.txt
     exit 1
   fi
   ```

2. **Triage the underlying transient.** Was 20:25Z–01:53Z a known Anthropic API incident, a key rotation, a model-routing change for `claude-opus-4-7`, or a quota cap? Without operator-side observability (key rotation log, status.anthropic.com) the cause can't be pinned down from inside the workflow.

3. **Optionally reset stale counters.** `memory/cron-state.json` `total_failures` reflects months of accumulated failures; consider zeroing per-skill counters once the workflow patch lands so health skills get a clean signal.
