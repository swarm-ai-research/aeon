## Symptom

Every scheduled skill in the window failed with the same error signature recorded
in `memory/cron-state.json`:

```
"...","total_cost_usd":0,"usage":{"input_tokens":0,"cache_creation_input_tokens":0,
"cache_read_input_tokens":0,"output_tokens":0,...}
```

`scripts/skill-runs --hours 168` reported 899/912 failures (~0.9% success rate).
33 of 38 tracked skills hit >100 consecutive failures.

## Evidence

- Failed run `27856646818` (self-review, 2026-06-20T01:52Z) — env shows
  `CLAUDE_CODE_OAUTH_TOKEN:` (blank).
- Succeeded run `27862412997` (gitlawb-fleet-metrics, 2026-06-20T06:07Z) — env shows
  `CLAUDE_CODE_OAUTH_TOKEN: ***` (set, masked). 1858 output tokens, 36s duration.

## Why we didn't notice for two weeks

Every monitoring skill (`skill-health`, `heartbeat`, `batch-health`, `skill-evals`,
`skill-repair`, `memory-flush`) was itself failing for the same reason. The
monitoring path shared the broken dependency with the monitored path.

## Recommendations

1. **Credential canary** in `aeon.yml` (pre-flight check) that exits with a distinct
   error message when both `ANTHROPIC_API_KEY` and `CLAUDE_CODE_OAUTH_TOKEN` are
   empty. Saves ~1 min of wasted CI per failure and produces a clear signal.
2. **Out-of-band reliability monitor** — a tiny pinger (different account / status
   page heartbeat) that alerts when zero Aeon skills succeeded in the last 6h.
   This is the only way to detect a total-auth outage.
3. **Move to resolved** once 3 consecutive days of healthy runs are confirmed
   and clear `last_error` / `consecutive_failures` for affected skills.
